# 真机验证矩阵

> 本文档是**发布的门**，不是参考说明。四端各自的「可用」结论只能来自这里的通过记录；
> CI 绿、构建成功、产物结构对，都**不能**替代它。
>
> 建立于 2026-09-25（v1.6.0 起生效）。对应路线图 [需求 1](ROADMAP.md)。

---

## 一、为什么需要这张表

项目有两条**已经证明过**的防线：

| 防线 | 能证明 | 在哪里 |
|---|---|---|
| 数值层 | 同一套评分逻辑，Python 与 TS **逐位等价** | `npm run verify:parity`（7 段） |
| 产物层 | 包里的前端**就是**本次构建的 dist；后端 exe 能起服务、`/api/health` 通 | `verify:source` / `verify:backend` / CI 冒烟 |
| 界面层 | 五端运行时 × 三页能**渲染出应有的界面**、路由与平台判定正确 | `npm run verify:ui`（2026-09 新增） |

它们一起仍然证明不了**第三件事**：

> 这个包，**装到真机上，用户能从头到尾用一遍吗？**

这一层恰恰全是「错了就闪退 / 永久黑屏 / 点了没反应」的地方，而且**不在任何自动化守卫的射程内**：

- 安卓权限桥（`MainActivity.CameraChromeClient`）—— WebView 的权限回调
- iOS `Info.plist` 的 `NSCameraUsageDescription` —— **缺失时进程被系统直接终止**，看起来像崩溃
- 真机 WebView 的 `getUserMedia` / `play()` / IndexedDB 行为 —— 与桌面 Chrome 不是同一套实现
- 切后台后 WebView 被冻结 —— 只能在真机上观察到

历史证据：**Android 最后一次真机验证是 v1.3.4**，此后权限桥反复改动（2026-09-24 才改成
`extends BridgeWebChromeClient`），**一次都没再上过真机**；mac / iOS 的 GUI 与摄像头
**一次都没在真机跑过**。也就是说 Android/macOS/iOS 三端当前处于「发了，但没人证明过能用」的状态。

别以为 Windows 就例外：它**能**在本机验（§五），但**也从没被按 §三 走完整清单**，
所以 §四 里它同样是「待验证」。四端一个都跑不掉。

## 二、判定规则（先定规则，再填表）

1. **每端至少一行「通过」**，才允许在任何对外文字（README / Release 说明 / 文档）里
   把该端描述为「可用」。没有通过记录的平台，一律写「未验证」。
2. **一行 = 一次完整的验证**，必须走完 §三 的 7 条路径，**不允许部分通过算通过**。
   某条不过就记「不通过」并写清现象，**仍然保留这一行**（失败记录同样是资产）。
3. **每条结论都要有可复现的证据**：命令输出、截图、日志、CI run 链接。
   「我试了没问题」不算证据。
4. **换过密钥 / 改过权限桥 / 改过 `Info.plist` / 动过打包配置之后，对应的行作废**，
   必须重验。这三处是「改一行、崩一片」的典型。
5. 记录**产物版本 + 产物 sha256**，而不是「最新版」。否则过两周没人说得清验的是哪一版。

## 三、固定验证路径（每端同一张清单，逐条打勾）

顺序固定，不要跳步 —— 后面几步依赖前面已经建立的状态。

| # | 路径 | 具体做什么 | 期望 | 证据形式 |
|---|---|---|---|---|
| 1 | **首次启动** | 全新安装（先卸载旧版）后打开 | 出界面，**不闪退**；桌面端不出现「正在启动服务…」卡死 | 截图 |
| 2 | **权限授权** | 授予摄像头权限；**再走一遍「拒绝 → 关掉应用 → 重新打开 → 允许」** | 拒绝时给出**可照做**的提示（不是空白/崩溃）；重新允许后能自动恢复正常 | 截图 ×2 + 录屏 |
| 3 | **监测出分** | 对着摄像头坐 30 秒，故意歪头 | 画面出来、分数动起来、指标数值随姿态变化 | 截图 |
| 4 | **触发提醒** | 把提醒间隔调到最小（2 分钟）等一次 | 收到**系统级**通知；点它能回到应用 | 截图 |
| 5 | **完成活动** | 做完一次「肩颈活动」全程 | 能走到结束；`activity_log` 落一条记录（仪表盘能看到） | 截图 |
| 6 | **切后台 / 锁屏 → 回前台** | 切后台 5 分钟 + 锁屏 5 分钟，再回前台 | **记录现状**：检测是否恢复、错过的提醒是否补发（当前为已知缺失，见 `MULTIPLATFORM.md §七`） | 录屏 |
| 7 | **退出重进** | 完全杀掉进程再打开 | 之前的数据、设置**都还在**；不要求重新授权（除系统策略外） | 截图 ×2 |

🔴 第 2 条里的「**拒绝后再允许**」是**最容易漏、也最容易崩**的一条：
Android 的 `permissionListener` 是**单个共享字段**，并发会互相覆盖，历史上因此出现过
**永久 pending**（界面永远停在"正在申请相机权限"）。这条必须真机走，模拟器与浏览器都复现不了。

### 4.3 发布放行记录（每放行一次，追加一行）

「发布」与「真机通过」是**两件不同的事**。§二.1 这条门限制的是**怎么说话**，不是**能不能发**：
真机门未满足时**可以**发布，但对外文字必须逐端写明「验到哪一步」，且不许出现"可用"。
于是每次「带着未满足的真机门对外发布」都要在这里留一行 —— 它是**决定记录**，不是通过记录。

（v1.6.0 建表之前发布的版本没有记录，本表从建表后第一次放行起记。）

| 日期 | 版本 | 发布状态 | 放行时四端真机门 | 对外措辞 | 决定 |
|---|---|---|---|---|---|
| 2026-09-26 | **v1.6.2**（同一批放行 v1.6.1） | 正式（Latest） | **未满足** —— §4.1 四端全为「待验证」 | Release 正文与 README **逐端写明验到哪一步**，全篇无"可用" | 业主在知悉 §二.1 后明确决定：带已知风险放行 |

🔴 「已发布」**不能**被读成「已验证」。§4.1 的逐端状态**不因发布而改变**；

## 五、各端怎么验（本机可做的部分）

### Windows（唯一能在本机完成的一端）

```bash
# 1. 安装包就在本机
release2/NeckGuardian Setup 1.6.2.exe

# 2. 安装后按 §三 走 7 条路径；截图存到 docs/evidence/ 下（或你的任意目录）
```

⚠️ 注意：**开发模式跑通 ≠ 安装包跑通**。必须装安装包，因为打包后资源路径不同
（历史上托盘图标就因为按 `public/` 找资源而静默空白）。

### Android

```bash
adb install -r NeckGuardian-<v>-android-release.apk
# 走 §三 时同步取证：
adb exec-out screencap -p > step1-first-launch.png
adb logcat -d > logcat.txt          # 重点搜 SecurityException / Permission
adb shell dumpsys activity services | grep -i neckguardian
```

### macOS

```bash
spctl -a -vv NeckGuardian.app          # 未签名时会是 rejected，属已知项
xattr -l NeckGuardian.app              # 看 quarantine 属性
```

### iOS

当前**无法验证**（产物未签名）。这不是"没时间验"，是**缺付费 Apple 开发者账号**这个前置条件，
对应路线图需求 3。在账号到位前，任何关于 iOS「能用」的说法都不成立。

## 六、自动化守卫覆盖到哪一步（别混淆）

| §三 的路径 | `verify:ui` 无头 Chrome | 真机 |
|---|---|---|
| 1 首次启动（出界面、不闪退） | 🟡 部分：能证明「本次构建的前端在 5 种运行时平台下都渲染得出来」 | ✅ 唯一权威 |
| 2 权限授权（含拒绝→再允许） | ❌ 不能：无头环境没有摄像头，也无系统权限对话框 | ✅ 唯一权威 |
| 3 监测出分 | ❌ 不能：dist 里没有 MediaPipe wasm/模型（那是 `cap-build` 才补的） | ✅ 唯一权威 |
| 4 系统通知 | ❌ 不能 | ✅ 唯一权威 |
| 5 完成活动（落库） | ❌ 不能 | ✅ 唯一权威 |
| 6 切后台 / 锁屏 | ❌ 不能 | ✅ 唯一权威 |
| 7 退出重进（数据还在） | ❌ 不能：无头环境每次都是全新 profile | ✅ 唯一权威 |

`verify:ui` 的价值是**便宜**（CI 每次跑，几十秒）和**早**（白屏 / 路由断 / 平台判定失效
在提交时就炸，而不是等发版后用户碰到），**不是**取代真机验证。
把它读成"UI 已经验过了"是这张表最想防住的事。

## 七、相关的已知未验证项（与本文档配套，别只读一处）

- 移动端**系统分享**导出通道、IndexedDB 的导入 / 清除路径 —— 只过了类型与逻辑层，无真机实测

- macOS / iOS 的 **Electron 窗口、摄像头链路、签名与 Gatekeeper、真机手感** —— 全部未验
- 动作库 `measurable`（只有 3 个动作可判定）—— 未经真机校准
