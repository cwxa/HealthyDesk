# 残余风险与覆盖台账

> 本文档回答一个问题：**「装上去能不能用」这件事，我们用什么证明，还剩什么证明不了。**
>
> **政策（2026-10-01）**：**真机验证不再是发布的门**。改用「**代码审查 + 单元测试（含静态守卫）**」
> 作为验证手段，并把代码验证**覆盖不到**的部分逐项登记为**已接受的残余风险**。
>
> 建立于 2026-09-25（v1.6.0，原名「真机验证矩阵」）。2026-10-01 按新政改造。
> 对应路线图 [需求 1](ROADMAP.md)。

---

## 一、为什么还留着这张表

项目有四层自动化防线：

| 防线 | 能证明 | 在哪里 |
|---|---|---|
| 数值层 | 同一套评分逻辑，Python 与 TS **逐位等价** | `npm run verify:parity`（7 段） |
| 产物层 | 包里的前端**就是**本次构建的 dist；后端 exe 能起服务 | `verify:source` / `verify:backend` |
| 界面层 | 五种运行时平台 × 三条路由能**渲染出应有的界面** | `npm run verify:ui`（352 项断言） |
| **原生层**（2026-10-01 新增） | **权限声明 / scheme / 包名配置正确**；**权限桥的并发收纳逻辑正确** | `verify:native-config`（10 项）+ `verify:android`（10 例 JVM 单测） |

这四层加在一起，仍然证明不了**第三件事**：

> 这个包，**装到真机上，用户能从头到尾用一遍吗？**

**这张表的价值不在于"要求去真机跑一遍"，而在于让"证明不了的那部分"无法被"一切都绿"掩盖。**

历史的教训没变 —— **「能构建 + 产物结构对 + CI 全绿」推不出「用户装上去能用」**。
变的只是落点：过去是"去真机上跑一遍清单"，现在是**逐项写清用什么覆盖、剩下的是什么、怎么处置**。

历史证据（仍然有效，值得记住）：Android 最后一次真机验证是 v1.3.4，此后权限桥改动数轮；
mac / iOS 的 GUI 与摄像头**一次都没在真机跑过**。

## 二、判定规则

1. **对外把某端描述为「可用」的条件**（2026-10-01 起）：
   - 该端相关的**全部自动化守卫为绿**（数值 / 产物 / 界面 / **原生配置** / **原生单元测试**），**且**
   - §三 里该端相关的**每一条残余风险都有处置结论**（见第 2 条）。

   两者缺一 ⇒ 不许对外说「可用」。**没有通过记录的平台，一律写「未验证」。**

2. **残余风险的处置只有三种，必须写明是哪一种**：

   | 处置 | 含义 | 去哪查 |
   |---|---|---|
   | `接受` | 影响面已知且可承受，业主决定带风险继续 | §4.3 放行记录 |
   | `规避` | 改设计让它不成立 | 写清改在哪 |
   | `待办` | 还没处理 | 登记为缺口，指向对应需求 |

3. 🔴 **不把「未验证」写成「已验证」。** 任何"某条路径从没跑过"的事实，必须能在本文档里查到 ——
   这是这张表存在的唯一理由。

4. **改过权限桥 / `Info.plist` / 打包配置之后，对应的覆盖结论要重算**（那三处是"改一行、崩一片"的典型）。
   注意现在要重算的是**守卫是否仍然覆盖它**（跑一遍守卫即可），不再需要重上真机。

## 三、风险登记

### A 类 · 已由代码验证覆盖（原先被误判为"只能真机验"）

这一类的共同点：**判据是静态文本或纯逻辑** —— 不需要设备。

| # | 原风险 | 现在的覆盖 | 在哪 |
|---|---|---|---|
| A1 | iOS 缺 `NSCameraUsageDescription` ⇒ 一开摄像头**被系统终止进程**（像闪退） | 静态守卫 + CI 对**包内 plist** 的复核 | `verify:native-config`；`build.yml` 的 macOS / iOS 打包 job |
| A2 | Android 缺 `CAMERA` 声明 ⇒ WebView 权限请求**必然被拒** | 静态守卫 | `verify:native-config` |
| A3 | 设了 `iosScheme` ⇒ iOS 本地页面加载不出来；设了 `hostname` 带端口 ⇒ `getUserMedia` 报 AbortError | 静态守卫（**剥掉注释后**判断，见下） | `verify:native-config` |
| A4 | 🔴 **权限桥并发请求互相覆盖 ⇒ 前端 `getUserMedia` 永久挂起**（v1.3.2「允许了权限却打不开」的机制） | **JVM 单元测试**：把收纳逻辑抽成不依赖 Android 框架的纯类 `CameraPermissionQueue`，10 例覆盖并发 / 看门狗 / 幂等 / 重入 | `CameraPermissionQueueTest`；`npm run verify:android`；CI 的 `android-unit-test` job |
| A5 | 用户把系统权限对话框挂着不点 ⇒ 前端永久转圈 | 单元测试覆盖看门狗（60s 后主动 deny）的**幂等性**：与系统回调谁先到都只应答一次 | 同上 |
| A6 | 界面白屏 / 路由指不到 / `?platform=` 覆盖失效 | 无头 Chrome 5 平台 × 3 路由 + 假摄像头喂帧 | `verify:ui`（352 项断言） |

🔴 **A3 的"剥注释"是必须的**：`Info.plist` 与 `capacitor.config.ts` 的注释里**恰好都提到了**
要禁用的键，写法与真声明几乎一样（例如注释里写着「故意不设 `iosScheme: 'https'`」）。
不剥注释就会把**正确的配置**判成错的。这道剥离器自带 7 例自测，并由变异测试证明必要。

### B 类 · 需要设备，但**只影响"能不能验"，不影响"能不能用"**

| # | 项 | 说明 |
|---|---|---|
| B1 | iOS 产物是**未签名 `.xcarchive`** | 不是 IPA，普通用户**装不上**。缺付费 Apple 开发者账号 —— 这与验证方式无关，是**产物**问题（路线图需求 3） |
| B2 | macOS 包未签名未公证 | 首次打开被 Gatekeeper 拦，需右键打开 |

> B 类**不是**"验证手段不足"。它们是"产物还不能直接分发给普通用户"，与本文档的验证政策是两件事。

### C 类 · 已接受的残余风险（原理上无法用代码验证）

| # | 残余风险 | 为什么代码验证**替代不了** | 影响面 | 处置 |
|---|---|---|---|---|
| C1 | **动作幅度阈值没有真人校准**（`MIN_POSE_MS = 200ms`、动作库 `measurable`） | 这是**物理量校准**，不是逻辑：判据本身没有真人数据支撑，跑多少单元测试都变不出真人 | "做得很快但到位"可能被判幅度不足；「肩部环绕」是未校准的取舍 | `接受`（§4.3），细节见 §七 |
| C2 | **真机 WebView 内核 ≠ 桌面 Chrome** | 环境不可复现：安卓/iOS 的 WebView 与桌面 Chrome 不是同一套实现 | 极少数 WebView 行为差异 | `接受` |
| C3 | **切后台 / 锁屏后 WebView 被冻结** | 只能在设备上观察 | 提醒在后台停发（已知缺失） | `接受` + 路线图需求 2（后台常驻）立项 |
| C4 | **移动端系统分享 / IndexedDB 导入清除路径** | 依赖系统 UI 与真机存储行为 | 分享失败无提示 | `接受` |
| C5 | **首帧 / 末帧的孤立抖动仍会偷走基线** | 要判"末帧算不算回位"需要方向信息，而三个姿态量全是 `abs()` ⇒ 特征层没有左右方向 | 动作最开头一帧异常时会高估一次活动幅度 | **明确不修**（已知缺口，**不是**待验证项） |

> ⚠️ C 类**不许**被读成"验过就没问题"，也不许被读成"待验证" ——
> 它们是**业主已知情并接受**的取舍。每次带着它们对外发布，都会在 §4.3 留一行。

## 六、覆盖边界（别把"绿"读成"全验过"）

原「7 条真机验证路径」逐条对应到现在的覆盖方式：

| 原路径 | 现在怎么覆盖 | 剩余（C 类） |
|---|---|---|
| 1 首次启动（出界面、不闪退） | `verify:ui` 证明「本次构建的前端在 5 种运行时平台下都渲染得出来」+ 产物层 | 真机安装器 / 包管理器行为 |
| 2 权限授权（含**拒绝 → 再允许**） | 🔴 **单元测试**：并发收纳 / 看门狗幂等（A4、A5）+ 静态守卫：权限声明齐备（A1、A2） | 系统权限**对话框本身** |
| 3 监测出分 | `verify:ui` 的假摄像头喂帧（有帧路径）+ `verify:parity`（数值逐位） | 真机摄像头**设备层**；C1 的校准 |
| 4 系统通知 | 无覆盖 —— 后台常驻尚未实现 | C3 |
| 5 完成活动（落库） | `verify:ui`（收尾屏 + 落库探针）+ `verify:schema`（迁移不丢数据） | 真机 IndexedDB 行为 |
| 6 切后台 / 锁屏 | 无覆盖 | C3 |
| 7 退出重进（数据还在） | `verify:schema` + 界面层的存储探针 | 真机进程生命周期 |

`verify:ui` 的价值是**便宜**（CI 每次跑，几十秒）和**早**（白屏 / 路由断 / 平台判定失效

## 七、已接受残余风险的细节（与本文档配套，别只读一处）

### C1 · 动作幅度阈值未经真人校准

- 🔴 **动作幅度阈值（v1.7.0 改动）**。v1.7.0 把"幅度"改成
  「该动作声明的那个量 · 在本段的活动范围 ÷ 该量的静息阈值」，阈值**复用静息提醒线**
  （不另立刻度）。"动作做多大才算到位"这件事本身**没有任何真人数据支撑**。
  - 具体待验（**需真人**）：**做一个标准的「颈部左侧屈」，幅度分是否落到 80 以上**（正常距离）；
    以及**「肩部环绕」** —— 它是唯一用 `metric: 'any'`（双侧对称、单一量测不到）的动作。
  - 🔴 **若真机上总判"幅度不够"，正确的修法是把它的 `measurable` 改成 `false`（不判也不提示），
    不是调阈值** —— 阈值一旦为单个动作特调，就与静息提醒线脱钩，
    `verify:exercise-quality` 的 a2 会立刻红。
  - 这一项**无法**由任何现有守卫覆盖：无头环境没有摄像头，判定阈值只能由真人对齐。**属 C 类。**
- 🔴 **时间支撑窗口 `MIN_POSE_MS = 200ms`（v1.7.1 新增）**。
  它把"占时不足 200ms 的孤立极值"从幅度里剔掉，用来挡"一帧抖动偷走基线"。
  - 若要验（**需真机 + 真人**）：一次真实的快速动作（很快地绕一圈肩、快节奏的侧屈）
    会不会因为"每个位都站不满 200ms"被判幅度不足。
  - 注意方向：帧率越低，一帧代表的时间越长 ⇒ **越不容易被剔**；
    风险落在"**高帧率 + 动作很快**"这个组合上。
  - 若真出现"动作做得又快又到位却判没动"，正确修法是**放宽这个常量**
    （并把新值同步进常量对拍与生成器），**不是**删掉那些反例用例 ——
    删用例等于把"一帧抖动偷基线"的旧缺陷放回来。
- 动作库 `measurable`（只有 3 个动作可判定）—— 同样没有真人校准。

### C5 · 首帧 / 末帧孤立抖动

- 🔴 **首帧 / 末帧的孤立抖动仍会偷走基线**（`_support_filtered()` 只处理"两侧都有邻居段"的段，
  见模块文档「已知未覆盖」）。表现：**动作最开头那一帧异常时高估一次活动幅度**。
- 这一条是**明确不修**（要判末帧算不算回位需要方向信息，而三个姿态量全是 `abs()`
  ⇒ 特征层没有左右方向），所以它是**已知缺口**而不是"待验证项" ——
  别读成"验过就没问题"。
