# NeckGuardian 评分与动作系统 · 迭代设计

> **范围**：`backend/services/scorer.py` ↔ `src/platform/localPoseEngine.ts` 的评分链路，
> 以及 `ExercisePanel` / `NeckActivity` 的动作执行链路（含两者的衔接处）。
> **不含**：分发、性能、数据保留、主题、AI —— 那些在 [ROADMAP.md](ROADMAP.md)。
>
> **与 ROADMAP.md 的关系**：本文档**展开并取代** ROADMAP 需求 7（锻炼内容自适应与扩展）的
> 粗粒度描述 —— 因为细化时发现「动作和评分在互相打架」这个更根本的问题，它比"多几个动作"
> 重要得多。ROADMAP 需求 6（姿态基线自学习）**不在本文档**：那是"阈值个性化"，
> 本文档聚焦"评分与动作的逻辑正确性"。两者都碰评分链路，**不可并行**（见 §六）。
>
> 编号用 S1–S10，与 ROADMAP 的 1–10 区分，避免交叉引用时混淆。

## 零、系统现状（本文档所有判断的依据）

### 0.1 评分链路

```
摄像头帧 → 角度(head_angle / shoulder_diff / spine_angle)
        → EMA 平滑(α=0.35)  ← smoother.py ↔ PoseSmoother
        → 分段扣分 → 加权合成 → 取整
        → { score, issues[] }
```

- 扣分分档（`scorer.py:34-44`）：轻微 22–28 / 明显 34–46 / 严重 52–65 分
- 三项合成（`scorer.py:83`）：`最差项算满 + 其余 × 0.3`
- 阈值内另有预警区（阈值 60% 起，每项最多 6 分）
- 核心不变量：**issues 非空 ⟺ 分数 < 80**
- 该链路的守卫已相当扎实：`verify:parity` = 21 常量 + 80 用例 + 42 序列/439 帧 + 8 角度

### 0.2 动作链路

```
7 个动作硬编码 (ExercisePanel.tsx:18-26)
  → setInterval 倒计时 (NeckActivity.tsx:379-399)
  → 期间持续采集「静息姿态分」进 sessionScores (NeckActivity.tsx:279-281)
  → 结束：平均值写入 recordActivity.avg_score (NeckActivity.tsx:352-372)
```

7 个动作、固定顺序、**12×6+10 = 82 秒**、无分级、无完成度判定、与用户实际问题无关。

### 0.3 三处实锤缺陷（带证据，非推测）

#### 缺陷 1 🔴 做对动作 = 被判「姿态异常」+ 被语音批评

评分函数**没有上下文**：`compute_score(head, shoulder, spine)`（`scorer.py:68`）只看三个当前
角度，**不知道用户此刻正在做康复动作**。而康复动作的定义就是"把头摆到非中立位"。

用真实评分函数实测（肩/脊柱端正）：

| 头部侧屈（`颈部左侧屈` 的正常活动范围） | 得分 | issues |
|---|---|---|
| 8° | 75 | 头部轻微侧倾 |
| 12° | 64 | 头部明显侧倾 |
| **20°** | **45** | **头部严重侧倾** |
| 30° / 45° | 35 / 35 | 头部严重侧倾 |

正常颈椎侧屈活动度约 45°，也就是说**用户把 `颈部左侧屈` 这个动作做到位，就必然被判
「头部严重侧倾」、拿到 35–45 分**。后果链：

1. 界面评分环变红、文案「姿态异常」（`NeckActivity.tsx:421-422`）
2. **语音播报「检测到头部严重侧倾，请注意调整坐姿。」** —— `NeckActivity.tsx:274-277` 的
   `speakPostureIssue` **没有 mode 判断**，运动态照样触发
3. 这 35–45 分被收进 `sessionScores`，平均后写入 `recordActivity.avg_score`
4. Dashboard 活动列表按 `avg_score >= 80 ? 绿 : >=60 ? 橙 : 红`（`Dashboard.tsx:185,210`）渲染
   → **用户每次认真完成活动，都留下一条红色低分记录**

**一句话：现在的产品在惩罚用户做它要求做的事。**

#### 缺陷 2 🔴 Dashboard 的「部位健康度」是编造的

`Dashboard.tsx:94-96`：

```tsx
<HealthBar label="头部" value={85} color="#4CAF50" />                        // 写死 85
<HealthBar label="肩部" value={summary?.today_avg ? Math.min(100, summary.today_avg + 5) : 0} ... />  // 凭空 +5
<HealthBar label="脊柱" value={summary?.today_avg ?? 0} ... />              // 直接用总平均
```

三个"部位健康度"**没有一个是该部位的真实聚合**：头部恒定 85 分（与数据无关），肩部是
总分加 5，脊柱是总分。而 `posture_score` 表**已经存了** `head_angle` / `shoulder_diff` /
`spine_angle` 三个分项（`database.py:29-36`、`localDb.ts:57-60`）—— 真实数据是有的，没被用。

#### 缺陷 3 🔴 「姿态质量驱动提醒」的设计意图存在，但从未实现

`config.py` 定义了三个常量，**全项目零引用**（`grep` 实证）：

| 常量 | 位置 | 引用数 |
|---|---|---|
| `LOW_SCORE_THRESHOLD = 60` | `config.py:19` | **0** |
| `CONSECUTIVE_LOW_COUNT = 3` | `config.py:20` | **0** |
| `POSTURE_CHECK_DURATION = 60` | `config.py:17` | **0** |

提醒的触发条件只有一条：`_accumulated_minutes >= interval`（`scheduler.py:165`），
即**纯按坐够多少分钟**。姿态好不好、分数高不高，对提醒**没有任何影响**。
`_minute_tick` 里唯一与姿态相关的写入是 `usage_record`（`scheduler.py:133-141`），
它和评分是两条互不相交的线。

### 0.4 结构性缺口

| # | 缺口 | 证据 |
|---|---|---|
| 1 | 评分**没有时间维度**：只有瞬时帧分，没人算"你今天歪着坐了 47 分钟" | `scorer.py` 签名只吃三个角度 |
| 2 | 评分**不可解释**：只返回总分 + issues 文案，没有"哪项扣了多少" | `scorer.py:116-122` |
| 3 | 动作**无完成度判定**：只有倒计时，用户做没做、幅度够不够，系统完全不知道 | `NeckActivity.tsx:379-399` 仅 `setInterval` |
| 4 | 动作与问题**无关联**：不管你是头偏还是肩不平，都是同一套固定顺序 | `ExercisePanel.tsx:18-26` 无维度标签 |
| 5 | `posture_score` 无 `issues` / `mode` 字段 → 事后无法区分"静息坐姿"与"活动中的姿态" | `database.py:29-36`、`localDb.ts:57-60` |
| 6 | 两条链路**都没有 schema 迁移机制** → 加字段必须先建迁移能力 | `database.py:21` 仅 `CREATE TABLE IF NOT EXISTS`；`localDb.ts:18` `DB_VERSION=1` 且 `onupgradeneeded` 只有建表分支 |
| 7 | ~~动作总时长在**三处各算一遍**~~ ✅ 已解决（S7）：此前 `NeckActivity.tsx` 两处 + 组件各算一遍 → 易漂移 | 已收敛为 `src/data/exercises.ts` 的 `TOTAL_DURATION_SEC` **单点定义**；守卫断言「数据文件之外不得再出现 `s + e.duration`」 |

### 0.5 顺带修正一个既有表述

README 的 FAQ 写「80–89 是死区」，**略窄**。精确的不可达区间是 **79–89（11 个整数分）**，
可数学证明：

- 三项**都不超标** → 每项最多扣 6 分 → `total ≤ 6 + 0.3×(6+6) = 9.6` → 分数 **≥ 90**
- **任一**项超标 → 该项至少扣 `MILD_BASE = 22` → `total ≥ 22` → 分数 **≤ 78**

实测佐证：三项恰好压在阈值 → **90 分**；头部从 5.00° 变成 5.01° → **94 → 78**。

## 一、排序原则

延续 [ROADMAP.md §一](ROADMAP.md) 的四条，针对子系统追加两条：

1. **先修"逻辑错误"，再谈"能力增强"。** 缺陷 1 不是"评不准"，是**评反了** ——
   系统惩罚用户做它要求的动作。任何新功能（更多动作、自适应序列、激励体系）在它之上都是坏投资。
2. **不做没有验证手段的改动。** 本项目评分链路的验证能力（四层对拍 + 变异测试）是它最可靠的
   资产。新增的每一条评分逻辑，都要能落进同一套对拍体系，否则宁可不做。
3. **不要展示不能证明的数字。** 缺陷 2 是"编造数据"级别的问题 —— 健康类应用里，
   假数字比没有数字更糟。
4. **一次只碰一个敏感区**（承 ROADMAP）。本文档中 **S1 / S4 都改 `scorer.py` 的返回值**，
   必须串行；**S1 与 ROADMAP 需求 6 都改评分语义**，不可并行。

## 二、批次 A：让评分与动作不再互相打架（P0）

### S1 · 评分引入「静息 / 运动」双通道 ✅ 已完成 🔴 最高优先

**【现状证据】** 见 §0.3 缺陷 1：`compute_score` 无上下文参数；`NeckActivity.tsx:274-277`
的语音批评无 mode 判断；`NeckActivity.tsx:279-281` 把静息分收进 `sessionScores`。
实测：做 `颈部左侧屈` 到 20° → 45 分 + 「头部严重侧倾」+ 语音批评。

> **实施记录**
> - **模式如何传**：桌面端评分在 Python 后端算，所以 `mode` 随 WS 帧一起发
>   （`{type:'frame', data, mode}`）。旧版前端不发或发非法值 → 后端回落静息态，
>   与分通道前行为完全一致（可灰度）。
> - **运动态度量**：三项相对各自静息阈值的倍数取最大 → 映射到 0–100。
>   复用静息阈值当标尺，让「活动量 1.0」有明确含义（偏离已达提醒线 = 确实动起来了）。
> - **额外发现并修掉的两处**：
>   1. 「达标与否」若用原始活动量判定，会出现 `raw = 59.94` 取整成 **60**（达标线）
>      却仍提示"幅度不足"的自相矛盾 —— 改为以**取整后的分数**判定。
>   2. 模式切换时平滑器状态未清空 → 会拿「运动中」的 EMA 值去评静息态，
>      活动结束后约 1 秒内出现虚假报警。两端都加了切换即 `reset()`。
> - **顺带止血**：活动期间不再写 `posture_score`（那些采样是运动态语义，
>   写库会污染「今日平均分」与 S3 的部位健康度）。

**【要做什么】**
1. 评分增加**模式维度**。静息态（monitor）保持现有语义**一字不变**；运动态（exercise）
   走**独立评分通道**，语义从"你对称吗"改为"这个动作做到位了吗"。
2. 运动态**不得产出静息类 issues 文案**（「头部严重侧倾」这类措辞在运动态是错的），
   也**不得触发** `speakPostureIssue`。
3. `sessionScores` 的语义要明确：从"活动期间的静息姿态分"改为"运动态通道的分数"。
   静息基线若仍需采集，另立字段，不混用。

**【验收标准】（可证伪）** —— 全部达成
- ✅ **静息态逐位不变**：`npm run verify:parity` 全绿（24 常量 + 80 用例 + 42 序列/439 帧 + 8 角度），
  **一个数字都不许变**。
- ✅ **运动态新断言**：`neck 侧屈 20°` → 运动态 **100 分、completed=true、issues 为空**；
  32 条运动态用例均**不含**「侧倾」「不平衡」「倾斜」任何静息类措辞。
- ✅ **语音隔离**：源码级守卫断言 `speakPostureIssue` 的每一处调用都落在
  `mode === 'monitor'` 分支内（node 侧没有 React 渲染环境，退一步做源码断言；
  它拦不住所有写法，但足以拦住「有人删掉 mode 判断」这个回归）。
- ✅ **变异测试**：三条各自针对一处守卫 —— 改静息态常量一位 / 运动态混入静息措辞 /
  去掉语音 mode 判断，`verify-scoring.mjs` 均 `exit 1`，且报错原因正确。
- ✅ **不变量分域声明**：静息态「issues 非空 ⟺ 分数 < 80」；运动态
  「issues 非空 ⟺ 分数 < 60（`EXERCISE_SCORE_BASE`）」。两者都在测试里分域断言，
  并在 `DEVELOPMENT.md` §4.1.1 写明适用范围。

**【风险 / 依赖】**
- 🔴 **最高危改动**。它碰的是项目唯一有严格对拍的核心资产。**必须独立成一次提交、单独跑 CI。**
- 静息态"逐位不变"是硬约束 —— 任何为了让两端对齐而放宽对拍的做法都不可接受。

### S2 · 动作完成度识别（做没做 / 幅度够不够 / 保持够不够久）✅ 已完成

**【现状证据】** `NeckActivity.tsx:379-399` 只有 `setInterval` 倒计时；
`sessionScores` 收集的是姿态分（见缺陷 1），**与动作质量无关**。
即：用户从头到尾不动，系统也会在 82 秒后照常宣布「活动完成!」并记一条记录。

> **实施记录**（与下面原设计的四处偏差，都是做的过程中才暴露的）
> 1. **样本存的是「三个指标」而不是原始 landmark**。原设计写"把 landmark 序列录成
>    样本文件"，但离线回放要**确定性**：33×4 个 landmark 送回 MediaPipe 才能得到角度，
>    而那段推理在 node 里跑不出可复现结果，样本也就无法在 CI 里比对。
>    落点改为存 `{t, head_angle, shoulder_diff, spine_angle}` —— 即
>    **判定函数真正的输入**；`landmark → 角度` 那一步已有独立守卫
>    （`verify-angles.mjs` 的 8 条用例），不需要在样本层重复覆盖。
> 2. 🔴 **发现"三个指标有一半动作测不到"，这是设计的硬伤**。
>    `exerciseActivity` 只看「头部侧倾角 / 肩部高度差 / 脊柱倾斜角」，本质是
>    **不对称与倾斜**。于是：颈部左右转（绕垂直轴旋转，正对摄像头时耳线仍水平）、
>    扩胸（双侧对称）、头部后缩（矢状面平移）在这三个量上几乎不动 ——
>    对它们判"没检测到动作"就是**冤枉正在认真做的用户**，与 S2 想消灭的
>    "产品惩罚用户"是同一类缺陷。落点：动作库加 `measurable` 字段，
>    7 个动作里只有 3 个（左右侧屈、肩部环绕）参与判定，其余**不判也不提示**，
>    收尾页明确写出「另有 N 个动作当前摄像头角度无法判定，未计入」。
>    ⚠️ 这张表按指标定义推出，**尚未用真机数据校准**。
> 3. **收尾文案从两种改成三种**。原设计隐含"完成 / 没完成"二分，模拟整场活动时发现：
>    一个"动了但幅度不足"的用户会被冠上「本次没检测到动作」——文案与判定互相打脸。
>    落点：`verdict` 增加 `moved` 维度，分「完成 / 动作做到了但幅度还可以更大 /
>    没检测到动作」三种（语音同源分三种）。`judged === 0`（没拍到人）时什么都不断言。
> 4. **实时引导窗口取 5 秒而不是 3 秒**。往复类要求窗口内含一次完整的
>    「到位→归位」，3 秒窗口会让慢速画圈（约 3 秒/圈）的人一直卡在
>    「再多做几次」的误报上 —— 这是离线模拟（`E:\tmp-verify\sim-session.py`）跑出来的。
>
> 交付物：`backend/services/exercise_quality.py`、`src/platform/exerciseQuality.ts`、
> `scripts/samples/exercise-{neck-left-flex,sit-still,too-shallow}.json`、
> `scripts/gen-exercise-quality-cases.py`、`scripts/verify-exercise-quality.mjs`
> （已挂进 `verify:parity`）。
>
> **未做**：`recordActivity.avg_score` 的语义仍是"运动态达成度平均"而非"完成度成绩"
> —— 那是 S10 的范围，且要先有 schema 迁移能力。

**【要做什么】**
1. 先建**离线样本能力**：把一段 `landmark` 序列录成固定格式的样本文件，
   可离线回放。没有这个，下面的判定逻辑无法被验证（这是前置条件，不是可选项）。
2. 基于序列做三类判定：
   - **有效活动幅度**：目标关节的活动量是否达到该动作的期望区间
   - **保持时长**：达标状态累计持续了多久（而非"倒了 12 秒计时"）
   - **有效次数**：往复类动作（环绕、扩胸）的有效循环计数
3. 判定结果驱动界面的**实时引导**（如"幅度再大一点""保持住"），
   而不是只显示一个倒计时。

**【验收标准】（可证伪）** —— 全部达成
- ✅ 三段固定样本（**正常完成 / 全程不动 / 幅度不足**）离线回放，判定函数给出**三种不同结论**，
  且结果可复现（纯函数 + 固定输入 → 固定输出）。守卫会断言三种结论两两不同，
  并断言"负样本不得被判为完成"。
- ✅ 判定阈值是**具名常量**并进入对拍体系（`verify-exercise-quality.mjs` 比对 17 个常量；
  29 条用例覆盖边界、数据中断、滞回计数、取整平局点）。
- ✅ **负样本必须失败**：「全程不动」的样本被判为"完成"时，测试必须红
  （变异测试 M9 验证过：把 idle 判定废掉，生成阶段就被样本自检挡下）。
- ✅ 实时引导已接入：手机端是画面内浮层，桌面端是固定高度占位的一行。

**【风险 / 依赖】**
- 依赖 S1：如果不先分通道，完成度判定会被静息评分污染，结论不可信。 ✅ 已具备
- 设备差异（摄像头距离/角度）会显著影响幅度判定 → 判定应基于**归一化量**（如相对肩宽），
  与现有 `shoulder_diff` 用百分比而非像素同一思路。
  ✅ 实际做法：复用 S1 的活动量（各项除以**自己的阈值**），天生归一化。

### S3 · 部位健康度统计去伪 ✅ 已完成

**【现状证据】** §0.3 缺陷 2：`Dashboard.tsx:94-96` 头部写死 85、肩部 `today_avg + 5`、
脊柱 = `today_avg`。分项数据在库里躺着没被用。

> **实施记录**（与下面原设计的三处偏差，都是做的过程中才暴露的）
> 1. **留证比预想更严重**：不只是"三个值互不相同"失败 —— 构造「头部严重侧倾（真实 35 分）、
>    肩部端正」的采样，旧口径给出头部 **85 分**，比肩部的 40 分还高。
>    即**最差的部位显示最高分，且头部数值与数据完全无关**（0° 和 30° 都显示 85）。
> 2. **顺带修掉一个真实的双端不一致**：`localStats` 算「应休息次数」时误用了保留一位

### S4 · 扣分明细与改进指引

### S5 · 「不良姿态累计时长」：给评分补上时间维度

**【现状证据】** 评分是瞬时帧分（`scorer.py:68`）；采样每 1.5 秒落一条
（`NeckActivity.tsx:283`），但**没有任何地方把采样序列折成时间量**。
Dashboard 的「今日平均评分」是采样平均，**它掩盖了分布** ——
"坐 8 小时里歪了 3 小时"和"偶尔歪一下"可能给出同样的平均分。

**【要做什么】** 基于采样序列计算：
- **不良姿态累计时长**（分数 < 80 的总时长）与**占比**
- **最长连续不良时长**（比累计值更能说明问题）
- 这两个量取代"平均分"成为上报的核心指标（平均分保留为辅助）

**【验收标准】（可证伪）**
- ✅ 构造一段合成采样序列，其中低分段落的**真实时长已知** →
  算法输出与真值误差 **< 一个采样间隔（1.5s）**。
- ✅ 序列中"5 段各 1 分钟的不良"与"1 段连续 5 分钟的不良"累计值相同、
  **最长连续值必须不同**（区分聚合与连续，防止实现只做求和）。
- ✅ 空序列 / 单点序列 / 全为 `no_pose` 的序列都不崩，返回 0 而非 `NaN`。

**【风险 / 依赖】**
- 依赖采样密度：1.5 秒间隔对"时长"够用，但**对"最长连续"的边界有 ±1.5s 误差** —— 
  验收标准里已按此放宽，不是缺陷是口径。
- 若同时做 S6，两者都读采样序列 → 可共用聚合函数。

### S6 · 让姿态质量真正参与提醒决策（激活死配置）

**【现状证据】** §0.3 缺陷 3：`LOW_SCORE_THRESHOLD` / `CONSECUTIVE_LOW_COUNT` /
`POSTURE_CHECK_DURATION` **定义了但零引用**；提醒只按 `usage_minutes`（`scheduler.py:165`）。

**【要做什么】** 二选一，**不允许第三种状态**（既留着又不用是最坏的）：
- **激活**：连续 N 次低分 → 提前触发提醒（用户已经歪着了，不必等满 30 分钟）
- **删除**：明确"本项目只做定时提醒"，把死常量删掉，并把这个决定写进文档

建议选**激活**，但要处理优先级冲突：提前提醒不得打断正在进行中的活动
（`_break_active` 已存在，需接入）。

**【验收标准】（可证伪）**
- ✅ 调度器决策逻辑抽成**纯函数**（不依赖全局状态），可单测：
  给定"连续 3 次低分"→ 返回"应提前提醒"；给定"低分但间隔不足"→ 返回"不提醒"。
- ✅ 进行中的活动（`_break_active`）**不被提前提醒打断**。
- ✅ 决策后 `grep` 这三个常量**不再有"定义未用"的项**。
- ✅ 该逻辑是**纯调度计算**，不碰 `scorer.py` → 可与 S1/S4 并行。

**【风险 / 依赖】**
- 需要 S5 的采样序列分析作为输入（"连续 3 次低分"要能判定）。
- 提醒变多是**用户可感知的行为变化** → 需要设置项开关，且默认行为不该让老用户

### 硬约束（违反会出真问题）

1. 🔴 **S1 与 S4 必须串行。** 两者都改 `scorer.py` 的签名/返回结构，
   并行会制造无法归因的 `verify:parity` 失败。
2. 🔴 **S1 的"静息态逐位不变"是硬约束。** 21 常量 + 80 用例 + 42 序列/439 帧 + 8 角度
   必须**一个数字都不变**。运动态是**新增通道**，不是修改现有公式。
3. 🔴 **S1 与 ROADMAP 需求 6（基线自学习）不可并行。** 两者都改评分语义，
   同时做会无法判断"分数变了"是谁导致的。
4. 🔴 **不做 schema 迁移就不加字段。** 现在两端都只有建表逻辑
   （`database.py:21`、`localDb.ts:52-68`），加字段会静默失败或丢数据。
   S10（乃至 S2 的序列存储）都要先有迁移能力。
5. 🔴 **新逻辑必须能被证伪。** 每条评分/判定逻辑都要有"构造反例 → 断言失败"的用例。
   本项目已经吃过三次"结论下早了"的亏，其中一次就是 CI 守卫自身的解析 bug
   却报"密钥变了"。
6. ⚠️ **双端一致**：任何评分/聚合/判定逻辑，若同时存在于 Python 与 TS，
   必须纳入 `verify:parity`；**不许退回内联副本**（副本会与源码各错各的，测试还全绿）。

## 七、暂不做的（明确记下来，避免反复讨论）

| 不做的事 | 理由 |
|---|---|
| **个性化阈值自学习**（每人一套基线） | 需要大量真机数据才有意义，而项目**目前没有真机验证手段**（ROADMAP 需求 1）。先做 S5 把时间维度补上，收益更大且不需要新数据。见 ROADMAP 需求 6。 |

| **活动成绩云同步 / 社交排行** | 与项目"数据不出设备"的隐私边界冲突（移动端推理全本地是**刻意设计**）。 |
| **呼吸节拍引导 / 背景音乐** | 属于体验锦上添花，排在 S1–S10 之后。 |
