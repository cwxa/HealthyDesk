## 一、排序原则

四个原则，按优先级解释为什么需求顺序是这样：

1. **可验证性优先。** 本项目已经吃过三次「结论下早了」的亏（列表接口延迟、`grep` 截断 `&&` 链、
   CI 守卫自身解析错却报「密钥变了」）。**一个改动如果没法被证明生效，等于没改**。所以
   需求 1 是「建立验证能力」本身，排在最前。
2. **硬缺口优先于新功能。** 「切后台就不提醒」「mac 装了打不开」是用户**直接感知不可用**，
   优先于打卡、主题这类锦上添花。
3. **数据风险优先于体验优化。** 见 0.3 #4：数据只增不删、且不可导出。这类债越晚改越贵
   （等用户攒了一年数据，schema 迁移和清理策略都要考虑存量）。
4. **一次只碰一个敏感区。** 项目有两个高危区：**双端评分一致性**（核心不变量：issues 非空 ⟺
   分数 < 80）与**安卓权限桥**（v1.3.2 的「永久 pending」就出在这）。这两处的改动不要并行，
   且各自必须配真机/对拍验证。

## 二、迭代 A：先让「能用」可被证明（P0）

### 需求 1 · 真机验证矩阵与 UI 冒烟

- **优先级** P0 ｜ **规模** 中 ｜ **依赖** 无 ｜ **阻塞** 需求 2、3、6、10 的验收
- **状态** 🟡 **部分完成**（v1.6.0）。第 3 项（UI 冒烟自动化）与第 2/4 项的**文档与门**已落地；
  **第 1、2 项的「真机通过行」未完成** —— 需要真机（Android）/ Mac / Windows 桌面，
  只能在有设备时做。详见下方「实施记录」与 `docs/device-matrix.md`。

**现状**：这是项目最大的空洞。CI 能证明「可构建、产物结构对、内置后端能在 Mac 上起服务」，
但**没有任何一次真机 GUI 验证**。而权限桥（安卓）与 `Info.plist`（iOS）恰恰是
「错了就闪退/永久黑屏」的地方。

**要做什么**

1. 定义**固定验证路径**（每端同一张清单，逐条打勾）：
   首启 → 权限授权（含「拒绝后再允许」）→ 监测出分 → 触发一次提醒 → 完成一次活动 →
   切后台/锁屏再回前台 → 退出重进（数据还在）
2. 建 `docs/device-matrix.md`：机型 / OS 版本 / 产物版本 / 每条路径结论 / 证据（截图或 CI run 链接）。
   **每端至少一行"通过"才允许把该端说成可用**。
3. UI 冒烟自动化：用 `?platform=` / `?os=` URL 覆盖在无头 Chrome 里跑三页渲染与交互
   （本机已有无头 Chrome 按手机视口验证的经验），纳入 CI 作为最便宜的一道网。
4. 把「真机验证」写进发布前清单，作为**发布的门**而不是事后补充。

**验收标准**

- `docs/device-matrix.md` 存在，Android（真机）与 macOS（真机）各至少一行通过记录，附证据
- 无头 UI 冒烟在 CI 里跑起来，且**故意改坏一处渲染能让它失败**（守卫必须用变异测试证明有效）

**风险**：iOS 真机需要 Apple 开发者账号（与需求 3 共用前置条件）。

**实施记录（v1.6.0）**

| 项 | 落点 | 状态 |
| --- | --- | --- |
| 1 固定验证路径 | `docs/device-matrix.md §三`（7 条，逐条写清"做什么 / 期望 / 证据形式"） | ✅ 已定义 |
| 2 验证台账 | `docs/device-matrix.md §四`（判定规则 5 条 + 逐端状态表 + 通过记录模板） | ✅ 已建（**四端均为待验证**，如实记录） |
| 3 UI 冒烟 | `scripts/verify-ui-smoke.mjs`（`npm run verify:ui`）；CI 在 `verify` job 里跑 | ✅ 已纳入 CI |
| 4 发布的门 | `docs/MULTIPLATFORM.md §9.0`（新增，置于 9.1 之前） | ✅ 已成为清单首项 |

**验收标准的证明方式**

1. **UI 冒烟确实在跑**：`verify-ui-smoke.mjs` 用 Node 内置 http 静态服务 + Chrome DevTools Protocol
   直连（**零依赖**：Node 22 起自带 `WebSocket`，不引 playwright/puppeteer），
   把 **5 种运行时平台 × 3 个路由**真实渲染一遍，共 **75 项断言**。
   CI 里已是一条独立步骤，找不到浏览器时**显式失败**（不静默跳过）。
2. **守卫有效（变异测试 4/4）**：`.buildenv/mutate-ui-smoke.py` 植入 4 种回归，
   要求冒烟**退出码非 0 且失败原因指向正确那一处**：

   | 变异 | 期望命中的断言 |
   |---|---|
   | M1 删掉 `/settings` 路由 | `#/settings` 渲染超时 |
   | M2 `runtime.ts` 不再采纳 `?platform=` 覆盖 | 设置页自报平台（`桌面版 (Windows)（桌面端）`） |
   | M3 Dashboard 页头文案写坏 | `#/dashboard` 渲染超时 |
   | M4 `package.json` 版本与界面兜底串脱钩 | 设置页自报版本不一致 |

   ⚠️ 变异测试**不进 CI**（要重构建 4 次，实测整轮约 **8–10 分钟**）：它验的是"守卫本身有效"，
   属于**改动守卫时**才跑的一次性证据，不是每次提交都跑的门。

**仍然没做到（不当作已完成）**

- 🔴 **四端都没有真机「通过」行**。UI 冒烟能覆盖的只是"界面渲染得出来"这一层，
  摄像头授权、系统通知、切后台、数据持久都不在它的射程内（对照表见 `device-matrix.md §六`）。
  也就是说：**四端（含 Windows）当前都不满足"可以说可用"的判据**。
- iOS 因缺付费开发者账号，**当前连验的条件都不具备**（产物是未签名归档，不可安装）。
- `Android` 的「拒绝权限后再允许」一条**必须**真机走：模拟器与浏览器都复现不了
  `permissionListener` 被并发覆盖导致的永久 pending。

### 需求 2 · 移动端后台常驻

- **优先级** P0 ｜ **规模** 大 ｜ **依赖** 需求 1（权限/通知路径必须可验）

**现状**：安卓/iOS 切后台后 WebView 被系统冻结 → 检测与提醒全停。用户在 README 与
`MULTIPLATFORM.md §七` 里被明确告知「这不是 bug」，但这是**产品层最大的功能缺失**：
一个提醒类 App 在手机上不提醒，等于核心价值归零。

**要做什么**

1. **Android 前台服务**：新增 `PostureMonitorService`（常驻通知 + 承载提醒计时）；
   `AndroidManifest` 补 `FOREGROUND_SERVICE`、`FOREGROUND_SERVICE_HEALTH`（Android 14+ 需声明类型）、
   `POST_NOTIFICATIONS`（Android 13+ 运行时申请）、`SCHEDULE_EXACT_ALARM`（按需）
2. **桥接口**：`NeckGuardianNative.setReminderSchedule(intervalMin, enabled)` / `cancel()`，
   前端在设置变更时同步；服务触发提醒时通过 `window.__ngReminder` 回灌
3. **前端降级**：服务不可用时回落到现有 `localReminder`（保持桌面语义不变）
4. **iOS 策略**：受系统限制，不做真正常驻；改为「回到前台时补发错过的提醒」+ 文档如实说明
5. **设置项**：常驻开关（默认开？需权衡——前台服务必然带一条常驻通知，用户可能反感），
   并在通知文案里说明用途

**验收标准**

- Android 真机：锁屏 30 分钟后仍收到提醒（截图 + `adb shell dumpsys activity services` 显示服务在跑）
- 切换常驻开关后，通知渠道随之创建/移除，`adb logcat` 无 `SecurityException`
- iOS：切回前台时补发错过的提醒（可验）

**风险**：🔴 直接触碰刚改过的权限桥区域（`CameraChromeClient`）。改动前先完成任务 1 的
安卓真机基线，否则出了问题无法判断是新引入还是原有。另外前台服务涉及**电量与用户观感**，
与需求 5 的性能基线要一起看。

### 需求 3 · 分发可用性：mac 签名公证 + iOS 可安装产物

- **优先级** P0 ｜ **规模** 中 ｜ **依赖** 需求 1（公证后需真机验 Gatekeeper）

**现状**：mac 包未签名未公证 → 用户首次打开被 Gatekeeper 拦，需要右键打开或
`xattr -dr com.apple.quarantine`；iOS 产物是**未签名归档，普通用户根本装不上**。
也就是说这两端当前处于「发了，但用不了」的状态，Release 说明里只能如实标注。

**要做什么**

1. **macOS**：Developer ID Application 证书签名（含 hardened runtime + entitlements）→
   `notarytool` 公证 → `stapler staple`；CI 增 `MAC_CERT_P12` / `MAC_CERT_PASSWORD` /
   `APPLE_ID` / `APPLE_TEAM_ID` / `APPLE_APP_PASSWORD` secrets
2. **iOS**：开发者账号导出 IPA（先 ad-hoc / TestFlight 内测），CI 增证书与描述文件
3. **产物断言扩充**（延续现有做法）：`codesign -dv` 校验签名主体、`spctl -a -vv` 期望 `accepted`、
   `xcrun stapler validate` 校验公证、IPA 内 `embedded.mobileprovision` 存在
4. 文档：README 去掉「右键打开」的绕行说明，改为正常安装

**验收标准**

- `spctl -a -vv NeckGuardian.app` 输出 `accepted`；`stapler validate` 通过
- 产出可安装 `.ipa`（`embedded.mobileprovision` 在内、`codesign -dv` 主体正确）
- CI 用**变异测试**证明断言会拦（如故意去掉签名步骤应 fail）

**风险**：需要付费 Apple 开发者账号（$99/年）；证书私钥保管是长期责任
（与安卓 keystore 同级别的「丢了就完了」资产）。**未获账号前，本需求无法启动**——
所以它虽然标 P0，实际是「账号到位即可开工」。

## 三、迭代 B：数据与性能的地基（P1）

### 需求 4 · 数据保留、聚合与导出/导入

- **优先级** P1 ｜ **规模** 大 ｜ **依赖** 无（但越早越好，见排序原则 3）
- **状态** ✅ **已完成**（v1.5.0）。分两次提交：`15ed236`（上半：迁移 + 归档 + 保留）、
  `3174e74`（下半：导出/导入 + 清除 + 用量 + 保留期可配置）

**现状**：`NeckActivity.tsx:283` 每 1500ms 写一条姿态记录，**全项目零清理逻辑**。
按每天 8 小时算约 1.9 万条/天、57 万条/月；移动端 IndexedDB 在 iOS 上有配额压力，
桌面端 SQLite 一年可到数百 MB。同时**没有任何导出途径**，移动端「卸载即清除」= 数据永久丢失。
数据库目前只有 `CREATE TABLE IF NOT EXISTS`，**没有迁移机制**（改 schema 无法演进）。

**要做什么**

1. **引入 schema 版本与迁移**：SQLite 加 `schema_version` 表 + 顺序迁移；
   IndexedDB 递增 `DB_VERSION` 并在 `onupgradeneeded` 里分支处理
2. **保留策略 + 日粒度聚合**：新增 `posture_daily`（日期、均分、最低分、采样数、各问题占比），
   原始采样只保留最近 N 天（N 可配，默认 30）后删除；聚合在**两端同语义**实现
   （`backend/` 与 `src/platform/`）
3. **导出 / 导入**：统一 JSON 格式（含版本号与两端字段全集），桌面与移动导出的文件**互相可导入**；
   提供 CSV 便于用户自己看
4. **一键清除全部数据**（设置页，二次确认）
5. **存储用量显示**：桌面取 DB 文件大小，移动用 `navigator.storage.estimate()`

**验收标准**

- 注入 30 天假数据跑聚合：原始表条数 ≤ 阈值，`posture_daily` 条数 == 天数，
  且聚合前后**当日均分与原始记录算出来的一致**（同源，不允许两处各算一遍）
- 导出→导入 round-trip：导入后统计数字与导出前逐项相等
- 迁移测试：用旧 schema 的库启动，能升到新 schema 且不丢数据

**风险**：聚合口径必须与仪表盘现有 `getSummary()` / `getWeekly()` 保持一致，
否则会出现「趋势图和周报对不上」这类极难排查的问题。建议**聚合口径只实现一次**，
让仪表盘改为消费聚合结果。

**实施记录（v1.5.0）**

| 落点 | 文件 |
| --- | --- |
| 迁移（桌面） | `backend/db/migrations.py`（3 条迁移）、`backend/db/database.py` |
| 迁移（移动） | `src/platform/localDb.ts`（`DB_VERSION` 1→2） |
| 日聚合纯函数 | `backend/services/daily_agg.py` ↔ `src/platform/dailyAgg.ts` |
| 保留与维护 | `backend/services/retention.py` ↔ `src/platform/localMaintenance.ts` |
| 导出格式 | `backend/services/export_format.py` ↔ `src/platform/exportFormat.ts` |
| 数据管理接口 | `backend/api/data.py`（status / export / export.csv / import / clear / maintain） |
| 数据管理层 | `src/platform/dataLayer.ts`、`src/platform/localData.ts` |
| 文件存取通道 | `src/platform/dataFiles.ts`（桌面 `<a download>`，移动端系统分享面板） |
| 界面 | `src/pages/Settings.tsx`「数据管理」区 |
| 守卫 | `scripts/verify-daily-agg.mjs`、`scripts/verify-export-format.mjs`（均挂在 `verify:parity`） |

三条验收标准的证明方式：

1. **聚合一致** —— `probe-retention.py`（40 天合成数据）逐字段复算 31 天，
   `probe-data-api.py` 断言「保留边界 = 本地今天 − 30 天的零点」「归档在清理后仍在」；
   `verify-daily-agg.mjs` 另有**可结合性不变量**（`merge([agg(a), agg(b)]) === agg(a ++ b)`），
   它从数学上保证跨天合并不漂移，并能抓住 `min_score` 这类忘记合并的字段。
2. **round-trip** —— `verify-export-format.mjs` 的 `e1` 断言 3 个包「导出 →（JSON 往返）→
   导入 → 再导出」逐字段不变；`probe-data-api.py` 另做**跨库**验证
   （A 库导出 → B 库导入 → B 库再导出逐字段相等）。
3. **迁移不丢数据** —— `probe-migrations.py` 覆盖四类库：老库（1000 条采样 + 自定义设置）、
   幂等重跑、半升级（有 v1 无 `posture_daily`）、全新库。

变异测试：`mutate-daily-agg.py` 9/9、`mutate-data-api.py` 12/12 全部被抓住且原因正确。

已知未验证项（不当作已完成）：
- 移动端的系统分享通道、IndexedDB 的导入/清除路径 —— 只过了类型与逻辑层，**没有真机/浏览器实测**。
- `posture_daily` 在桌面端报 `schema_version = 3`、移动端报 2：两者是**各自存储的结构版本**
  （移动端那一步是 `onupgradeneeded`，桌面端多一条"补默认设置"的迁移），不可直接比较；
  导出文件里的 `schema_version` 只是诊断信息，导入时**不参与校验**（只校验 `format_version`）。

### 需求 5 · 性能与功耗基线及优化

- **优先级** P1 ｜ **规模** 中 ｜ **依赖** 需求 1（需真机测量）

**现状**：`usePoseEngine.ts` 用 `requestAnimationFrame` 全速 `detect()` ——
桌面 60fps 时每秒 60 次推理，移动端纯靠 WebView 自己撑；`camera_ws.py` 每帧都处理 640×480。
**推理帧率从未实测**，无任何 CPU / 内存 / 温度 / 电量数据。健康类 App 的差评第一来源就是耗电发热。

**要做什么**

1. **埋点**：前端环形缓冲记录 fps 与单帧耗时（p50/p95），设置页新增「诊断」区展示
   （已有 `nativeDiag` 基础设施可挂）
2. **可配帧率**：检测帧率档位（如 8 / 12 / 15 / 全速），默认值由测量决定；
   桌面端与移动端可不同
3. **长跑基线**：三端各跑 30 分钟，记录内存曲线（是否有泄漏）、CPU 占用、移动端温升与耗电
4. **优化候选**（按测量结果决定是否做）：推理输入降分辨率、隔帧推理+插值、
   `requestVideoFrameCallback` 替代 rAF、MediaPipe delegate 回退计数上报

**验收标准**

- `docs/performance.md` 有三端基线数据（fps、CPU%、30 分钟内存首尾对比）
- 🔴 **降帧不得改变评分数值语义**：`smoother` 是逐帧 EMA（α=0.35），降帧会改变收敛速度。
  必须用现有序列用例验证「降帧后序列输出一致」，或明确记录为**有意的语义变更**并更新用例
- 内存长跑无单调增长（首尾差在噪声范围内）

**风险**：与双端一致性铁律交叉。任何影响帧序列的处理都要过 `npm run verify:parity`。

### 需求 6 · 姿态基线自学习与灵敏度校准

- **优先级** P1 ｜ **规模** 大 ｜ **依赖** 需求 5（先有稳定帧率，基线才可复现）｜ 🔴 高危区

**现状**：三项阈值是**全人类共用常量**（`HEAD_TILT_THRESHOLD=5.0` 等）。但「正常坐姿」
个体差异极大：笔记本（低头）vs 外接屏（平视）、不同身高与肩宽。固定阈值必然导致
一部分人「一直报警」或者「从来不报警」。

**要做什么**

1. **基线采集**：首次使用引导一个 30 秒「自然坐姿」采集，取稳健统计量（中位数/分位）作为个人基线
2. **阈值派生**：判定改为「相对个人基线的偏移」而非绝对角；保留绝对上限兜底（防基线本身是驼背）
3. **灵敏度档位**：宽松 / 标准 / 严格（映射到偏移倍数），给不想做校准的用户默认值
4. 🔴 **双端同步实现**：`backend/services/scorer.py` 与 `src/platform/localPoseEngine.ts`
   必须同公式；`scripts/verify-scoring.mjs` 扩充「基线 × 灵敏度」组合用例
5. **数据层**：基线存 `settings`（两端同 key），需求 4 的导出格式需包含它

**验收标准**

- **核心不变量仍成立**：出现任何提醒（issues 非空）⟺ 分数 < 80，用扩充满的用例集验证
- 新增 parity 用例（至少 3 组基线 × 3 档灵敏度）全绿
- 校准前后对同一段视频输入的判定差异符合预期（放宽/收紧方向正确）

**风险**：🔴🔴 **这是项目最敏感的区域**。历史教训见 `MEMORY`：旧公式 `超量 × 0.7` 曾导致
「头偏 7° 提醒却只扣 1.4 分 → 99 分」。改动必须：扣分分档边界与 issues 分档判断
**共用同一组常量**；取整统一 `round(x*100)/100`（前端 `pyRound()`）；变异测试证明守卫有效。

### 需求 7 · 锻炼内容自适应与扩展

> ⚠️ **本条已被 [ROADMAP-SCORING.md](ROADMAP-SCORING.md) 展开并取代。**
> 细化到子系统时发现一个更根本的问题：**评分函数不知道用户正在做动作**，导致
> 「颈部左侧屈」做到 20° 会被判「头部严重侧倾」、拿 45 分、并被语音批评
> （实测，见该文档 §0.3）。在那之上做"更多动作 / 自适应序列"是坏投资。
> 本条对应其 **S7 动作库数据化 / S8 自适应序列与难度分级 / S9 安全约束与疼痛反馈**。
> 保留本节作为范围与验收的原始出处，**开工请以 ROADMAP-SCORING.md 为准**。

- **优先级** P1 ｜ **规模** 中 ｜ **依赖** 需求 4（需要聚合数据做推荐）

**现状**：`ExercisePanel.tsx` 里 **7 个动作写死、顺序固定、总 82 秒**。不管用户是头前倾
还是高低肩，做的都是同一套；做完记录一条 `activity_log` 就结束。README 提到「做完有积分奖励」，
但激励非常轻。

**要做什么**

1. **按问题定制序列**：用近期问题分布（哪个指标最差、占比多少）给动作加权排序，
   并在动作提示里说明「为什么给你安排这个」
2. **时长分级**：短（约 1 分钟，工间）/ 标准（约 3 分钟）/ 完整（约 5 分钟），
   由提醒场景（工间提醒 vs 主动进入）决定默认档
3. **动作库扩展**：补充可选的拉伸/力量动作（如胸椎旋转、斜方肌放松），带版本化配置
   （避免再写死在组件里 —— 抽成 `src/data/exercises.ts`）
4. **要领说明**：把现有 `hint` 扩展为「要领 / 常见错误 / 目标肌群」，可配语音播报

**验收标准**

- 给定 3 组不同问题分布 → 生成的序列不同，且**最差项对应的动作被前置或加时**
- 动作配置从组件中抽出，新增动作不改组件代码
- 活动完成写入 `activity_log`，`exercise_count` / `duration_sec` 与实际一致

**风险**：低。但改完必须回归移动端「肩颈活动」页的固定高度整屏布局
（该页不滚动，随数据出现/消失的提示必须是固定容器内的绝对定位浮层）。

## 四、迭代 C：体验与留存（P2）

### 需求 8 · 深色模式与设计令牌统一

- **优先级** P2 ｜ **规模** 中 ｜ **依赖** 需求 7（页面结构稳定后再统一样式成本更低）

**现状**：**没有主题系统**。颜色大量内联硬编码（`'#999'`、`'#4CAF50'`、`'#2E7D32'`…），
只用了一部分 CSS 变量。图标集里已经有 `MoonIcon` / `SunIcon` 却完全没被使用——
说明「深色模式」是被规划过但没做的。

**要做什么**

1. 抽 `src/styles/tokens.css`：颜色（语义化命名）、间距、字号、圆角、阴影
2. 支持 **浅色 / 深色 / 跟随系统**（`prefers-color-scheme`），用户选择持久化到 `settings`
3. 逐页替换硬编码色值；用脚本扫描残留的十六进制字面量作为**可量化的完成度指标**
4. 桌面端接 Electron `nativeTheme`，托盘图标随主题切换（已有 `tray-iconTemplate` 的 mac 分支）

**验收标准**

- 组件里不再出现裸十六进制色值（扫描脚本 0 命中，允许白名单）
- 深色模式下**三页 × 两端**截图检查：无浅底深字、无对比度不足
- 移动端「肩颈活动」页固定布局在两种主题下都不跳（该页有整屏不滚动的约束）

**风险**：低，但覆盖面广、容易漏。建议按页提交，每次附截图。

### 需求 9 · 连续打卡、周报与激励体系

- **优先级** P2 ｜ **规模** 中 ｜ **依赖** 需求 4（聚合）、需求 7（活动内容）

**现状**：只有 `activity_log` 流水 + 仪表盘上「今日活动次数 / 完成率」两个数字。
没有连续天数、没有周报、没有里程碑。健康类产品的留存几乎全靠这一层。

**要做什么**

1. **连续打卡**：`streak_days` / `longest_streak`；补卡规则要明确（当天有 1 次活动即算）
2. **周报卡片**：本周均分、活动次数、最需改善的一项、与上周对比；刻意做成「可分享的卡片布局」
3. **里程碑**：7 / 30 / 100 天，达成时给一次轻提示（不做弹窗轰炸）
4. **数字同源**：周报数值直接消费需求 4 的 `posture_daily`，**不允许另算一遍**

**验收标准**

- 构造连续 7 天数据 → `streak_days == 7`；断一天 → 归零（或按补卡规则）
- 周报数字与聚合表逐项一致（写一个断言，防止两处口径漂移）
- 里程碑只触发一次（重复进入不重复提示）

**风险**：低。注意别把「打卡」做成压力源——这是肩颈健康 App，不是健身竞赛。

## 五、迭代 D：能力纵深（P3）

### 需求 10 · 移动端 AI 能力

- **优先级** P3 ｜ **规模** 中 ｜ **依赖** 需求 3（iOS 分发）、需求 4（数据导出与隐私边界）

**现状**：`Settings.tsx` 里整块 AI 设置被 `!isMobile()` 包起来 —— 移动端完全不提供 AI，
因为移动端没有后端（`hasLocalBackend()` 仅 electron 为 true）。

**要做什么**

1. **移动端直连**：BYO API Key，用户在设置页填自己的 Key，存本地（同样掩码显示、不上传）
2. **Prompt 同源**：把 `ai_advisor.py` 的 system prompt 与模板抽成**单一来源**
   （如 `shared/ai-prompts.json`，两端各自加载），避免桌面/移动措辞漂移
3. **降级链**：未配 Key / 断网 → 本地预设建议（移植 `fallback.py` 的逻辑到前端）
4. **隐私边界**：明确「只发三个角度数值 + 统计数字，不发画面」，并在首用时显式告知
5. （可选）**端侧小模型**：评估在 WebView 里跑轻量模型的可行性，作为完全离线的方案

**验收标准**

- Android 真机：配 Key 能生成结构化报告；无 Key 时降级路径可用且提示明确
- Prompt 与桌面端来自同一文件（改一处两端同时生效，有测试断言）
- 隐私说明与 README「隐私」章节一致

**风险**：Key 在客户端 = 暴露面。文档必须写清「只存本机、不上传、不代管」；
CORS 方面 DeepSeek 是否允许浏览器直连需先验证（不允许则改走「用户自建中转」方案，
或退回不做）。

## 六、依赖关系与批次

```
需求 1 真机验证矩阵 ──┬─→ 需求 2 后台常驻
                      ├─→ 需求 3 签名公证 ──→ 需求 10 移动端 AI
                      └─→ 需求 5 性能基线 ──→ 需求 6 基线自学习（高危）
需求 4 数据生命周期 ──┴─→ 需求 7 锻炼自适应 ──┬─→ 需求 8 深色模式
                                              └─→ 需求 9 打卡周报
```

| 批次 | 需求 | 主题 | 出口条件 |
|---|---|---|---|
| A | 1、2、3 | 先让「能用」可被证明 | Android/mac 真机清单各一行通过；mac 公证 `accepted` |
| B | 4、5、6、7 | 数据与性能地基 | 聚合 round-trip 通过；三端性能基线成文；不变量用例全绿 |
| C | 8、9 | 体验与留存 | 主题切换无硬编码色；周报数字与聚合表一致 |
| D | 10 | 能力纵深 | 移动端能出 AI 报告且 prompt 同源 |

**跨批次的硬约束**

- 🔴 需求 2 与需求 6 **不要并行**：一个碰权限桥、一个碰双端评分，都是高危区，
  出问题会互相干扰归因
- 需求 4 越早做越好：它是「数据只增不删」的止损，且需求 7/9 都依赖其聚合结果
- 需求 3 的启动前置条件是 Apple 开发者账号，账号未到位期间可先做需求 4/5
